Welcome to SyntraceAI

SyntraceAI is an adversarial mutation-testing agent for AI applications. It injects a deterministic bank of small bugs into a target codebase, runs that project's own test suite against every one of them in an isolated sandbox, and measures what the suite actually catches. Bugs that survive are auto-healed: it synthesizes assertion tests proven to kill them, and re-runs the campaign to show they do.

It exists because line coverage measures the wrong thing. Coverage counts lines executed; it says nothing about behavior defended. A suite can visit 90% of your code while asserting almost nothing about it, and prompt regressions - a lost instruction line, a renamed schema key, dropped few-shot examples - are invisible to line coverage by construction.

Every number in this documentation comes from a real, seeded, reproducible run. Nothing here is a projection, and nothing rendered in the app is a mock number.

The stack, in one paragraph

Python 3.11+ and nothing else that matters. The mutator is ast plus ast.unparse; the sandbox is shutil.copytree plus a pytest subprocess; the healer is a differential prober running candidate inputs through both the original and mutated module. There is no model call anywhere in the engine, no network access, and no API key. A campaign against the demo target costs $0.00 and takes about ten seconds.

How it works

Four stages. The first three diagnose, the fourth repairs.

1. Inject

Seven AST operator families produce code mutants - one mutation site per mutant - and twelve prompt perturbations attack the target's prompt module if it has one. Every mutant must survive compile() before it is allowed near a sandbox. Mutations that can be proven semantically inert are excluded from the bank up front, because an unkillable bug in the denominator would misstate every downstream score.

2. Isolate

Each bug is applied to its own fresh copy of the project in a temporary directory, and the project's real suite runs against it under a timeout, in parallel. Exit codes map to verdicts: 0 means the bug survived, 1 means the suite caught it, a timeout or a collection error counts as caught because the suite broke loudly. Silence never counts as detection.

3. Score

Killed over the frozen bank is the mutation score. Alongside it the baseline auditor measures line coverage on the same code with the same suite, so the two numbers sit side by side and the gap between them is the finding.

4. Heal

For every survivor, the healer searches for an input on which the original and the mutant disagree. If it finds one, it re-verifies that input in both project copies and only then writes a test. Survivors with no discriminating input are reported as likely-equivalent - never hidden, never quietly dropped from the denominator.

The shape of the result One command turns "we have 87% coverage" into "our tests catch 48% of real behavior changes, here are the 26 that slipped through, and here are 24 generated tests, each proven to kill a specific one." Diagnosis, evidence and repair ship together.

Install and run

Python 3.11+ (developed and verified on 3.14). No API keys, no network access.

pip install -r requirements.txt

python main.py full          # baseline audit (~3s) + full campaign (~8s)
python main.py baseline      # the coverage.py audit on its own
python main.py mutate        # the campaign on its own

python dashboard/server.py   # Mission Control at http://127.0.0.1:8377

The demo target

targets/sample_app is a deterministic AI ticket-triage pipeline: prompt templates, a rule-based mock LLM that reads its own instructions, pydantic contract validation with a deliberately lenient salvage path, and boundary-rich pricing and scoring logic. Its 48-test suite is green at 87.1% coverage with realistic blind spots - the suite a rushed team actually ships.

The mock LLM matters. Each contract line in the prompt has a real behavioral consequence: remove the JSON-only directive and it wraps its output in chatty prose; drop the few-shot examples and it forgets the summary field. That makes prompt perturbation measurable without a model call, deterministically, at zero cost.

Second, at exhaustive depth that 98%-coverage suite still misses 35 behavior changes, and the healer wrote 12 tests humanize's own suite lacks, pinning unit-scaling thresholds nobody had asserted:

assert humanize.number.intword(1e+18, '%.1f') == '1.0 quintillion'

The 23 remaining survivors at exhaustive depth are reported, not hidden: the isinf-guarded family, a mutant reachable only through a list[Any] signature the healer refuses, one intword power-table entry no probed magnitude reaches, and threshold arithmetic inside metric, intcomma, ordinal and fractional that the current input pools cannot discriminate.

Your own project

SyntraceAI is a local developer tool, not a hosted service. There is no account, no upload and no API key. It reads your source, mutates temporary copies, runs your suite against them, and deletes them. Your code never leaves your machine.

python advanced/run_mutation.py --target ~/code/my-app

If your layout is not app/ plus tests/, drop one file in your project root. This is the entire integration:

{ "source_package": "myapp", "tests_dir": "tests", "prompt_templates": null }

syntrace_target.json also takes an exclude list for modules you do not want mutated. prompt_templates points at your prompt module if you have one, which switches on the twelve prompt perturbations; leave it null for a code-only campaign.

You get back a terminal report, JSON and self-contained HTML under reports/ named for your project, and - the part you keep - new test files written into your project's own tests directory, each pinning behavior on an input verified to catch a specific bug. Review them and commit the ones you want.

Regenerated every run test_healed_assertions.py is deleted and rewritten at the start of every campaign, which is what makes runs reproducible. Copy anything you edit into a test file of your own before running again.

As a CI gate

python /path/to/SyntraceAI/advanced/run_mutation.py --target . --fail-under 90

This repo gates itself the same way. .github/workflows/ci.yml runs the selftests and three campaigns on Python 3.11 and 3.12 for every push to main and every pull request: the demo campaign at ≥95%, the humanize frozen bank at ≥85%, and the humanize exhaustive campaign at ≥88%.

AST mutation

Seven operator families, applied one site per mutant through ast.NodeTransformer and re-emitted with ast.unparse:

OperatorTransformation
ArithmeticOperatorSwap+ ↔ - · * ↔ / · // → / · % → *
ComparisonOperatorSwap== ↔ != · < ↔ <= · > ↔ >=
BooleanOperatorSwapand ↔ or
ConditionNegationif c: → if not c:
ConstantMutationn → n+1 · 0 → 1 · True ↔ False (docstrings skipped)
BoundaryValueMutationnumeric constant inside a comparison → ±1
ReturnValueMutationreturn expr → return None

Enumeration is deterministic, ordered by file path, line, column and operator name. Bank selection is a seeded round-robin stratified across file and operator, so a 38-mutant bank spans every file and every operator family rather than clustering in whichever module happens to have the most arithmetic. IDs M001… are assigned after selection, in selection order.

Equivalence exclusions

Two patterns are provably inert and are excluded before they can enter the bank:

  • An ordering-comparison swap inside a clamp pattern - if x > C: x = C with no else, a plain name and the same non-zero constant - is a semantic no-op under standard numeric semantics.
  • The TYPE_CHECKING idiom: if TYPE_CHECKING: guards are never negated and the constant in TYPE_CHECKING = False is never mutated, because those blocks are import-only at runtime.

Everything the provers cannot settle statically stays in the bank and is judged empirically. Equivalents that slip through surface honestly as unhealable survivors rather than being quietly removed from the denominator.

Prompt perturbation

Twelve perturbations, P001 through P012, each rewriting a constant in the target's prompt module through an AST-based replace_constant rather than string surgery. Code-only targets return none of them.

  1. RoleStripping - remove the role line from the system prompt.
  2. JsonOnlyDirectiveRemoval - remove the "respond only with JSON" directive.
  3. InstructionNegation - replace that directive with one inviting commentary.
  4. SchemaKeyRename - confidence → certainty.
  5. SchemaKeyRename - summary → synopsis.
  6. SchemaKeyRename - category → topic.
  7. TypeRuleRemoval - drop the integer-type rule for priority.
  8. RangeRuleRemoval - drop the numeric-range rule for confidence.
  9. SectionMarkerCorruption - corrupt the ### TICKET ### marker.
  10. SectionMarkerCorruption - remove the output-rules section entirely.
  11. WhitespaceNoise - insert a zero-width space inside a schema instruction.
  12. FewShotDrop - blank the few-shot example block.

A perturbation may never remove a {placeholder} that the template's .format call needs. That would crash the pipeline rather than degrade it, and a crash is not the failure mode being measured.

Why this is separate from code mutation A prompt is executable configuration. A renamed schema key or a dropped instruction line changes program behavior exactly the way a code edit does, but no coverage tool will ever register it - the prompt module's lines were "executed" either way.

Sandboxed evaluation

Every bug is evaluated in isolation. The runner copies the target to a fresh temporary directory, overwrites exactly one file with the patched source, and runs the project's suite there:

python -m pytest -q -x --no-header -p no:cacheprovider

The subprocess inherits the environment plus PYTHONDONTWRITEBYTECODE=1, is killed at its timeout, and its temporary directory is always cleaned up. Copies ignore __pycache__ and .pytest_cache. Nothing is ever mutated in place, so an interrupted campaign cannot leave your working tree damaged.

Outcome mapping

0SURVIVEDthe bug slipped through

otherERRORdetected - the suite broke loudly

Loud breakage counting as detection is a deliberate, stated choice: a suite that errors out has noticed something. In the shipped demo run this channel is unexercised - all 49 detections are genuine assertion failures, with zero timeouts and zero errors. You can check that yourself in reports/mutation_report.json.

Sandboxes run in a thread pool over subprocesses, defaulting to min(8, cpu_count()). Parallelism affects wall time only; verdicts are identical at any --jobs.

Differential healing

A survivor is a bug your suite did not notice. Healing turns each one into a test that would have.

For each survivor the healer generates candidate inputs and runs them through both the original and the mutated module in subprocess probes, looking for an input on which the two disagree. Candidates come from several pools:

  • Type-hint pools - scalar, union and alias-resolvable annotations (int, float, bool, str, None, float | str, a NumberOrString alias).
  • Harvested literals ±1 - the module's own constants and the boundaries either side of them, which is where mutation bugs actually live.
  • Pairwise string concatenations and non-integral floats.
  • Order-of-magnitude sweeps anchored on the function's own defaults.
  • Cross-function synthesis - the module's own str -> str functions compose realistic inputs such as fully rendered prompts, so the probe reaches states no flat pool would.

The honesty gate

A discriminating input is not enough to emit a test. The healer re-verifies it in both project copies first, and only a re-verified input becomes an assertion. No verified input, no test. Survivors with no discriminating input are reported as likely-equivalent or unhealable, with their reason, and they stay in the denominator.

Read the post-heal score correctly Post-heal detection is high by construction: every healed test is synthesized from an input already verified to discriminate its mutant, so the re-run kill is expected. The informative number is the pre-heal detection. The post-heal score measures that the healer's output is real and complete, not that healing is hard.

Reading the score

A campaign reports several numbers and they answer different questions. Confusing them is the main way mutation testing gets misread.

NumberWhat it answers
line coverageWhich lines ran. Says nothing about whether your tests would notice if those lines were wrong.
score_originalThe diagnosis. How many injected bugs your suite caught before any help. This is the honest measure of what your tests defend.
score_finalThe score after healing. Measures that the generated tests are real, not that the code got safer on its own.
healed_testsHow many survivors the healer could pin with a verified discriminating input.
survivorsEverything still uncaught, each with its file, line, operator and a reason if it is believed equivalent.

The gap between the first and second rows is the finding. On the demo target that is 87.1% against 48.0% - thirty-nine points of false confidence.

Report sets are named from the resolved target path, not the directory name. The bundled demo keeps the unprefixed names; other targets vendored under targets/ use their bare name; every other project gets its name plus a short digest of its absolute path, so two projects that merely share a directory name never collide and nothing external can ever land on the demo's committed filenames.

Mission Control

/app is the same engine with a face on it. It reads the same report files the CLI writes - nothing rendered there is a mock number.

  • Run against takes the path of any local Python project. The demo and humanize are one-click presets.
  • Run Mutation Campaign, Baseline and Full launch the same commands the CLI runs, streaming the engine log live.
  • The views in the sidebar break the result apart: detection by operator, surviving bugs, healed tests, the live log, and the agent trajectories.
  • Every result carries a provenance line saying whether you are looking at a stored result from an earlier run or something measured in this session. A saved run is never dressed up as a live one.

Report sets and reset

Each project writes its own report set, selectable from the dropdown in the header. Running a campaign against a new path adds a set; the dashboard switches to it when the run finishes.

Reset in the header offers two different things, because "reset" means two different things:

  • Clear the view blanks the tiles, panels and log so you can start from an empty screen. Nothing on disk is touched, and the choice is remembered per report set: it survives a reload and a trip to the landing page, and lifts when you restore it or run a campaign. Other report sets are unaffected - clearing the demo view does not blank humanize.
  • Delete saved reports removes that report set's files along with the healed-test file its campaign wrote. It lists every path before it will enable the button, and it refuses while a run is in progress.
Bundled sets are protected The demo and humanize report files are the committed evidence this documentation cites, so Reset refuses to delete them. Only report sets from your own projects can be cleared. A set whose origin cannot be established is protected too - refusing is the recoverable mistake.

Determinism

The engine is seeded and fully deterministic. Same seed means the identical bank and identical scores, on any machine, at any parallelism, on any supported Python version. Every verdict, mutant ID and healed test is reproducible.

Reports are byte-stable except for the single top-level wall_time_s field. You can diff two runs yourself and see only that line move.

Both the baseline auditor and the campaign delete any previously generated test_healed_assertions.py before measuring, so every run starts from the original un-hardened suite. Without that, a second run would audit the first run's repairs and report a flattering number.

Threats to validity

Stated up front, because a benchmark you cannot interrogate is a benchmark you cannot trust.

The demo target is self-authored, and the mock LLM's degradation rules are authored couplings

The mock keys off the same contract lines the perturbator attacks - by design. It simulates documented real-LLM failure modes (prose-wrapped JSON, dropped fields, hallucinated keys) deterministically at $0, so the prompt-side numbers validate the harness mechanics, not model behavior. The load-bearing, least-gameable numbers are the code-mutation rows: 18/38 → 37/38, plain AST mutations against a plain pytest suite.

Post-heal detection is high by construction

Covered in Differential healing. The diagnosis number is the pre-heal 48%.

Loud breakage counts as detection

Timeouts and collection errors map to detected. In the shipped run this channel is unexercised - all 49 detections are genuine assertion failures, verifiable in the committed report.

Generality limits

A target is declared by a one-file adapter, and the code half of the engine ran unchanged on humanize. The prompt half requires the documented template contract in docs/ARCHITECTURE.md §5.1.

Known limits

  • The healer probes top-level functions with scalar, union or alias-resolvable hints and refuses containers. A mutant reachable only through a list[Any] signature will be reported as unhealable rather than guessed at.
  • The equivalence provers cover clamp swaps and TYPE_CHECKING guards under documented assumptions. Everything else is judged empirically, which means genuine equivalents can appear as survivors.
  • The prompt half needs a prompt module matching the documented template contract. Point prompt_templates at null and you get a clean code-only campaign instead.
  • Input pools are finite. At exhaustive depth on humanize, threshold and format arithmetic in four functions could not be discriminated by the current pools; those are listed as survivors with reasons rather than hidden.
  • Targets must be Python with a pytest-runnable suite. There is no support for other languages or test runners.
The position Line coverage is a vanity metric. A 90%-coverage suite that catches 48% of injected bugs is not a safety net - it is a green dashboard over an open manhole. Mutation score, measured adversarially and healed automatically, is the metric that should gate AI-application CI.
